# Развёртывание: Supabase + Vercel

Инструкция описывает развёртывание пилота этапа 1. Порядок действий рассчитан
на то, что выполняется один раз одним человеком и занимает 40–60 минут.

---

## 0. Предварительное предупреждение

Прочитайте до начала работ — это влияет на выбор тарифа.

### Персональные данные

Закон РК «О персональных данных и их защите» требует хранения персональных данных
граждан РК в базах данных на территории Республики Казахстан. Supabase размещает
данные в дата-центрах за пределами РК (ближайший регион — Франкфурт).

**Следствие.** Пилотная эксплуатация допустима только на обезличенных или тестовых
данных. Работа с реальным контингентом требует переноса базы данных на инфраструктуру
в РК (собственный сервер вуза, VPS у казахстанского провайдера или Supabase
в self-hosted-варианте на сервере вуза).

Поскольку Supabase — это открытое ПО, миграция с облачного Supabase на self-hosted
не требует изменения кода приложения: меняются только `DATABASE_URL`, `DIRECT_URL`
и `NEXT_PUBLIC_SUPABASE_URL`. Это существенно снижает стоимость перехода на этапе 2.

### Тариф Vercel

Условия бесплатного тарифа Vercel Hobby прямо запрещают коммерческое использование.
Коммерческим считается любое развёртывание, приносящее финансовую выгоду **любому
участнику разработки, включая оплачиваемого исполнителя**. Платформа университета,
разрабатываемая на возмездной основе, под этот запрет подпадает. Нарушение влечёт
приостановку проекта без предупреждения.

**Варианты:**

| Вариант | Стоимость | Комментарий |
|---|---|---|
| Vercel Pro | 20 USD за пользователя в месяц | Разрешено коммерческое использование |
| Vercel Hobby | 0 | Только если разработка ведётся безвозмездно силами вуза |
| Собственный сервер вуза | стоимость сервера | Решает одновременно вопрос локализации ПДн |

Приложение — обычное Next.js-приложение и разворачивается на собственном сервере
командой `npm run build && npm start` за обратным прокси (nginx). Привязки к Vercel
в коде нет: используются только стандартные возможности Next.js и Vercel Cron,
который на своём сервере заменяется системным `cron` с вызовом тех же маршрутов
`/api/cron/*`.

## 1. Проект Supabase

1. Создайте проект на <https://supabase.com>. Регион — **Frankfurt (eu-central-1)**:
   ближайший к Казахстану из доступных, задержка около 80–110 мс.
2. Задайте надёжный пароль базы данных и сохраните его.
3. Нажмите кнопку **Connect** в верхней части панели проекта — понадобятся
   две строки (во вкладке **ORMs → Prisma** они выдаются готовой парой):

| Переменная | Что взять | Порт | Назначение |
|---|---|---|---|
| `DATABASE_URL` | Transaction pooler | 6543 | Используется приложением |
| `DIRECT_URL` | **Session pooler** | 5432 | Используется созданием схемы и миграциями |

> **Не используйте Direct connection** (`db.xxxxx.supabase.co`): на тарифах
> без платного IPv4-адреса он доступен только по IPv6, которого нет у Vercel.
> Session pooler работает по IPv4 и поддерживает подготовленные выражения,
> необходимые миграционному движку.

К строке пула обязательно добавьте параметры:

```
?pgbouncer=true&connection_limit=1
```

Без них Prisma на serverless-функциях Vercel исчерпает пул подключений при первой же
заметной нагрузке — например, при одновременном прохождении теста 300 студентами
(критерий приёмки № 14).

4. **Project Settings → API** — скопируйте:
   - `Project URL` → `NEXT_PUBLIC_SUPABASE_URL`
   - `anon public` → `NEXT_PUBLIC_SUPABASE_ANON_KEY`
   - `service_role` → `SUPABASE_SERVICE_ROLE_KEY`

> `service_role` обходит все политики доступа. Он используется **только на сервере**
> (`src/server/storage.ts`) и не должен попадать в клиентский код. В переменных Vercel
> его нельзя называть с префиксом `NEXT_PUBLIC_`.

## 1a. Row Level Security — обязательный шаг

> **Без этого шага база открыта всему интернету.** Проверено на этом проекте:
> до включения RLS анонимный ключ читал таблицу `users` вместе с
> `passwordHash` и `iinEncrypted`, а также изменял и удалял любые строки.

Supabase поднимает над базой публичный REST-интерфейс (PostgREST). Ключ
`NEXT_PUBLIC_SUPABASE_ANON_KEY` публичен по своей природе: префикс
`NEXT_PUBLIC_` встраивает его в JavaScript-бандл, и его видит любой посетитель
сайта. Единственное, что ограничивает этот ключ, — Row Level Security.

Prisma создаёт таблицы командой `db push` (или `migrate deploy`) и **RLS не
включает**. Пока платформа закрыта Deployment Protection, это незаметно; в тот
момент, когда ссылка становится публичной, база оказывается доступна на
чтение и запись.

Включение:

```bash
npm run db:rls
```

Скрипт `scripts/enable-rls.ts` выполняет `ALTER TABLE … ENABLE ROW LEVEL
SECURITY` для каждой таблицы схемы `public` и **не создаёт ни одной политики**.
Отсутствие политик означает «запрещено всем» для ролей `anon` и
`authenticated`.

На работу приложения это не влияет:

- Prisma подключается пользователем `postgres`, который владеет таблицами, а
  `ENABLE ROW LEVEL SECURITY` (в отличие от `FORCE ROW LEVEL SECURITY`) на
  владельца не распространяется;
- `@supabase/supabase-js` используется только на сервере и только с сервисным
  ключом, который RLS обходит штатно;
- анонимный ключ в коде не используется вообще.

**Запускать после каждого `db push` на новой базе** — новые таблицы создаются
с выключенным RLS.

### Как убедиться, что закрыто

```bash
curl -s "$NEXT_PUBLIC_SUPABASE_URL/rest/v1/users?select=email&limit=1"   -H "apikey: $NEXT_PUBLIC_SUPABASE_ANON_KEY"   -H "Authorization: Bearer $NEXT_PUBLIC_SUPABASE_ANON_KEY"
```

Должно вернуться `[]`. Если возвращаются реальные записи — RLS не включён.

Заодно проверьте, что бакеты хранилища не публичные (`public: false`) и что
серверные секреты не попали в клиентский бандл:

```bash
grep -rl "$SUPABASE_SERVICE_ROLE_KEY" .next/static   # должно быть пусто
```

## 2. Хранилище файлов

В **Storage** создайте два бакета, оба **приватные** (Public bucket — выключено):

| Бакет | Содержимое | Лимит файла |
|---|---|---|
| `materials` | Учебные материалы: PDF, презентации, документы | 100 МБ |
| `submissions` | Работы обучающихся по заданиям | 20 МБ |

Публичный доступ недопустим (раздел 6.3 ТЗ): все ссылки выдаются подписанными
со сроком действия 15 минут через маршрут `/api/files/[attachmentId]`, который
предварительно проверяет права доступа.

Загрузка идёт напрямую в хранилище по подписанной ссылке, минуя сервер приложения
(F-T-04). Это обязательно: тело запроса к serverless-функции Vercel ограничено
4,5 МБ, и загрузка 100-мегабайтного файла через сервер невозможна в принципе.

## 3. Переменные окружения

Сгенерируйте секреты:

```bash
openssl rand -base64 32   # AUTH_SECRET
openssl rand -base64 32   # IIN_ENCRYPTION_KEY — ровно 32 байта
openssl rand -hex 32      # CRON_SECRET
```

> **`IIN_ENCRYPTION_KEY` восстановлению не подлежит.** При его утрате все
> зашифрованные ИИН станут нечитаемыми. Сохраните ключ в защищённом хранилище вуза
> до первого запуска сида.

Полный перечень — в `.env.example`. Минимально необходимый набор:

```
DATABASE_URL, DIRECT_URL
NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY
AUTH_SECRET, AUTH_URL, AUTH_TRUST_HOST
IIN_ENCRYPTION_KEY
CRON_SECRET
```

## 4. Первая миграция

> Если вы разворачиваете пилот через браузер, без локальной установки —
> этот шаг пропускается: схема создаётся на сборке командой `prisma db push`,
> а справочники загружаются через `/api/setup`. См. `docs/QUICKSTART.md`.

Для промышленного контура выполняется локально, до развёртывания:

```bash
cp .env.example .env      # заполнить DATABASE_URL и DIRECT_URL от Supabase
npm install
npx prisma migrate dev --name init
```

Каталог `prisma/migrations/` **обязательно коммитится в репозиторий** — на Vercel
миграции применяются командой `prisma migrate deploy`, которая исполняет уже
готовые файлы и никогда не изменяет схему самостоятельно.

Загрузка справочников и демо-данных:

```bash
npm run db:seed                    # справочники + демо
SEED_DEMO=false npm run db:seed    # только обязательные справочники
```

Справочники (роли, шкалы оценивания Приложений 1 и 2, настройки системы)
загружаются идемпотентно — повторный запуск безопасен.

## 5. Развёртывание на Vercel

1. **Add New → Project**, подключите репозиторий.
2. Framework Preset определится автоматически как Next.js.
3. **Environment Variables** — добавьте все переменные из шага 3.
   `AUTH_URL` укажите равным итоговому домену (например,
   `https://lms.example.kz`), после первого развёртывания при необходимости
   поправьте.
4. Команда сборки задана в `vercel.json`:

```
prisma generate && next build
```

Схема в сборку намеренно не входит. Раньше здесь стоял
`prisma db push --skip-generate`, и любая недоступность базы роняла сборку
целиком — приложение нельзя было развернуть даже тогда, когда сам код исправен.
Схема приводится в соответствие отдельным шагом, до развёртывания:

```bash
npm run db:push     # prisma db push
```

**Для промышленной эксплуатации перейдите на миграции:** создайте локально
`npx prisma migrate dev --name init`, закоммитьте каталог `prisma/migrations/`
и применяйте `npm run db:deploy` (`prisma migrate deploy`) перед выкладкой.
Без истории миграций нельзя откатить неудачное изменение схемы и нельзя
воспроизвести состояние базы.

5. **Settings → Deployment Protection.** По умолчанию Vercel может включить
   **Vercel Authentication**: все запросы, включая `/api/auth/*`, редиректятся
   на `vercel.com/sso-api`, и войти может только владелец аккаунта Vercel.
   Для работающей платформы её нужно перевести в **Disabled** — иначе
   обучающиеся и преподаватели не смогут открыть даже страницу входа.

6. Регион исполнения — `fra1` (Франкфурт), задан в `vercel.json`. Он должен
   совпадать с регионом Supabase: разнесение регионов добавляет 100–200 мс
   к каждому запросу и не позволит уложиться в требование 500 мс по 95-му
   процентилю (раздел 6.1 ТЗ).

### Собственный домен

**Settings → Domains** → добавьте домен вуза, пропишите CNAME у регистратора.
После привязки обновите `AUTH_URL`: от него зависят ссылки в письмах,
метатеги Open Graph и `sitemap.xml`.

## 6. Задачи по расписанию

### Ограничения тарифа Hobby

Их важно знать заранее — иначе развёртывание завершится ошибкой:

| Ограничение Hobby | Значение |
|---|---|
| Частота запуска | **не чаще одного раза в сутки** |
| Количество задач | **не более двух** |

Расписание вида `*/10 * * * *` отклоняется на этапе развёртывания с сообщением
`Hobby accounts are limited to daily cron jobs`. Это ограничение тарифа,
одинаковое для всех бесплатных аккаунтов; смена аккаунта ничего не меняет.

### Конфигурация по умолчанию (Hobby)

В `vercel.json` задана **одна ежедневная задача**, выполняющая все регламентные
операции последовательно:

| Маршрут | Расписание | Что делает |
|---|---|---|
| `/api/cron/daily` | ежедневно в 02:00 | Очередь Platonus, закрытие повисших сессий учёта времени, уведомления о сроках сдачи, контроль квот |

Отказ одной операции не отменяет остальные — каждая выполняется независимо,
результат по каждой возвращается отдельным полем ответа.

### Конфигурация для тарифа Pro

Готовый файл лежит в репозитории — `vercel.pro.json`. При переходе на Pro
замените им `vercel.json`:

| Маршрут | Расписание | Назначение |
|---|---|---|
| `/api/cron/outbox` | каждые 10 минут | Отправка событий в Platonus, закрытие повисших сессий |
| `/api/cron/deadlines` | ежедневно в 06:00 | Уведомления о приближающихся сроках сдачи |
| `/api/cron/backup-check` | ежедневно в 03:00 | Контроль объёма БД и квот |

Десятиминутный интервал для очереди интеграции существенен только после
подключения API Platonus: он определяет задержку передачи оценок в учётную
систему. До подключения API (этап 2) суточного интервала достаточно.

### Защита маршрутов

Все маршруты `/api/cron/*` требуют заголовок `Authorization: Bearer $CRON_SECRET`.
Vercel подставляет его автоматически при наличии переменной `CRON_SECRET`.
Их можно вызвать и вручную — например, чтобы проверить работу или запустить
отправку в Platonus вне расписания.

## 7. Резервное копирование

Раздел 6.2 ТЗ требует: ежесуточное копирование, глубина хранения не менее 30 дней,
копия **отдельно от основной инфраструктуры**, и — что важнее всего — **практически
проверенная процедура восстановления** (критерий приёмки № 12).

Автоматических резервных копий Supabase недостаточно: они хранятся у того же
поставщика и на бесплатном тарифе имеют ограниченную глубину. Требуется независимая
выгрузка.

```bash
# Ежесуточная выгрузка в независимое хранилище
pg_dump "$DIRECT_URL" --format=custom --no-owner \
  --file="lms-$(date +%F).dump"

# Проверка восстановления на отдельной базе (выполнять до начала эксплуатации)
createdb lms_restore_test
pg_restore --dbname=lms_restore_test --no-owner "lms-$(date +%F).dump"
psql lms_restore_test -c "SELECT count(*) FROM users;"
```

Копии файлов из Supabase Storage выгружаются отдельно — они не входят в дамп БД
(раздел 6.2: «учебное содержимое реплицируется отдельно от базы данных»).

**Зафиксируйте в акте приёмки дату и результат проверки восстановления.**
Описанная, но не выполненная процедура критерию приёмки № 12 не удовлетворяет.

## 8. Квоты бесплатных тарифов

| Компонент | Квота Supabase Free | Оценка для 5 000 пользователей и 1 000 курсов |
|---|---|---|
| База данных | 500 МБ | Метаданные — единицы сотен МБ. Основной рост — `activity_logs` и `time_sessions` |
| Хранилище | 1 ГБ | Достаточно для PDF и презентаций; **видео не помещается** |
| Исходящий трафик | 5 ГБ в месяц | **Узкое место при активной эксплуатации** |
| Приостановка | после 7 дней без обращений | Первый запрос после простоя — с задержкой |

Меры при работе на бесплатном тарифе:

1. Мониторинг потребления с порогом оповещения 70 % — реализован
   в `/api/cron/backup-check`, уведомления приходят администраторам.
2. Видеоматериалы размещаются **только на корпоративном аккаунте вуза** на YouTube,
   а не на личных аккаунтах преподавателей. При увольнении преподавателя вуз иначе
   теряет учебный контент. Требование должно войти в регламент работы с Платформой.
3. Ведётся реестр всех внешних ссылок с указанием владельца — для последующей
   миграции на собственное хранилище.
4. Периодическая очистка `activity_logs` старше учебного года: агрегированные
   показатели сохраняются в `progress` и `item_completions`, детальный журнал
   активности нужен только для текущего периода.

## 9. Проверка после развёртывания

Пройдите по списку — он соответствует критериям приёмки раздела 11 ТЗ:

- [ ] Публичный каталог открывается без авторизации, учебное содержимое недоступно.
- [ ] Вход выполняется под каждой из ролей; при первом входе запрашивается согласие
      на обработку персональных данных.
- [ ] Преподаватель создаёт курс из не менее чем 10 элементов трёх типов
      и публикует его.
- [ ] Курс с несоответствием часов не публикуется, величина расхождения показана.
- [ ] Студент проходит курс; освоенные академические часы отображаются корректно.
- [ ] Тест из 20 вопросов четырёх типов проверяется автоматически, результат
      попадает в журнал.
- [ ] Итоговая оценка и буквенный эквивалент соответствуют Приложению 1.
- [ ] GPA подтверждён контрольным примером, посчитанным вручную.
- [ ] Ведомость выгружается в XLSX.
- [ ] Интерфейс полностью работает на трёх языках, непереведённых строк нет
      (`node scripts/build-messages.mjs --check`).
- [ ] Все сценарии обучающегося работают на экране шириной 360 px.
- [ ] Импорт 100 пользователей из XLSX проходит без ошибок.
- [ ] Резервная копия создана и **успешно восстановлена** на отдельном окружении.
- [ ] Журнал аудита фиксирует изменение оценки с прежним и новым значением.
- [ ] Нагрузочная проверка: 300 одновременных прохождений теста.

### Нагрузочная проверка

```bash
npx autocannon -c 300 -d 60 \
  -H "Cookie: authjs.session-token=<токен тестового пользователя>" \
  https://lms.example.kz/kk/my/courses/<id>/quiz/<quizId>
```

Контролируйте 95-й процентиль времени ответа (требование — не более 1,5 с для
страницы курса и 500 мс для API) и число подключений к БД в панели Supabase.
При исчерпании пула увеличьте `connection_limit` или перейдите на тариф с большим
пулом.

## 9a. Сбои развёртывания, которые уже случались

Ниже — реальные отказы этого проекта и их причины. Все они проявляются
одинаково («не деплоится»), но лечатся по-разному.

### Сборка падает: Can't reach database server at `db.<ref>.supabase.co:5432`

`DIRECT_URL` указывает на **Direct connection**. Этот хост на тарифах без
платного IPv4-адреса резолвится только в IPv6, а сборщик Vercel работает по
IPv4 — соединение не устанавливается в принципе.

Проверка:

```bash
nslookup db.<ref>.supabase.co          # только адрес вида 2a05:... — IPv6
nslookup aws-0-<region>.pooler.supabase.com   # адреса вида 18.198.x.x — IPv4
```

Решение: `DIRECT_URL` — тот же **пул**, что и `DATABASE_URL`, но порт 5432
(session mode) и без `pgbouncer=true`:

```
postgresql://postgres.<ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres
```

### Authentication failed against database server

Пароль скопирован вместе с квадратными скобками. Supabase показывает строку
подключения с плейсхолдером `[YOUR-PASSWORD]`, и скобки — часть плейсхолдера,
а не пароля. Строка `:[mypassword]@` не работает, нужна `:mypassword@`.

### Сид падает: IIN_ENCRYPTION_KEY должен быть 32 байта в base64

В переменную записаны 32 **hex**-символа — это 16 байт. Нужен ключ ровно в
32 байта, закодированный base64:

```bash
openssl rand -base64 32
```

Ключ менять нельзя после того, как в базе появились зашифрованные ИИН:
`decryptIin` перестанет их читать.

### Vercel отклоняет выкладку: Vulnerable version of Next.js detected

Сборка при этом проходит успешно, отказ происходит на шаге «Deploying outputs».
Vercel блокирует выкладку версий Next.js с известными критическими
уязвимостями (в частности CVE-2025-29927 — обход авторизации в middleware
через заголовок `x-middleware-subrequest`; приложение защищает маршруты именно
middleware, так что уязвимость здесь не теоретическая).

Решение — обновиться до актуального патча ветки и пересобрать:

```bash
npm install next@15.5.24 eslint-config-next@15.5.24
npm run verify
```

### Сайт открывается, но вход не работает: редирект на `vercel.com/sso-api`

Включена **Deployment Protection → Vercel Authentication**. Внешне сайт
отвечает `200`, но это страница-заглушка Vercel, а не приложение. Отключается
в Settings → Deployment Protection (см. раздел 5, пункт 5).

Быстрая проверка, что защита снята:

```bash
curl -s https://<домен>/api/auth/csrf     # ожидается JSON с csrfToken
```

Порядок работ, обязательных до начала эксплуатации с реальным контингентом:

4. Мониторинг и оповещения (Sentry уже предусмотрен в стеке).
5. Проверенная процедура восстановления, зафиксированная документально.
