# Перенос платформы на инфраструктуру университета

Порядок переноса с текущей площадки (Vercel + Supabase) на сервер вуза
или казахстанский VPS.

**Зачем.** Персональные данные граждан Республики Казахстан подлежат хранению
на территории РК. Текущая площадка размещает данные за пределами страны:
для пилота на обезличенных данных это допустимо, для промышленной
эксплуатации — нет.

---

## Что переносится

| Компонент | Сейчас | После переноса |
|---|---|---|
| Приложение | Vercel (серверные функции) | Node.js в контейнере на сервере вуза |
| База данных | PostgreSQL 16 на Supabase | PostgreSQL 16 на сервере вуза |
| Файлы работ и материалов | Supabase Storage | Вариант А: Supabase Storage self-hosted<br>Вариант Б: MinIO |
| Периодические задачи | Vercel Cron | systemd timer или cron |
| HTTPS-сертификат | Vercel | Caddy или nginx + Let's Encrypt |

**Что не меняется ни в одном варианте:** код бизнес-логики, схема базы данных,
модель доступа, интерфейс, тесты. Приложение обращается к базе по стандартному
протоколу PostgreSQL, поэтому смена площадки для базы — это смена строки
подключения.

---

## Развилка по файловому хранилищу

Это единственное место, где выбор влияет на объём работ. Вся работа с файлами
изолирована в одном файле — `src/server/storage.ts`, восемь функций.

### Вариант А. Supabase self-hosted — код не меняется

Supabase публикуется как набор контейнеров (`docker compose`), который
разворачивается на своём сервере. Приложение продолжает обращаться к тому же
API, меняются только `NEXT_PUBLIC_SUPABASE_URL` и ключи.

- **Правок в коде:** ноль.
- **Что поднимается:** PostgreSQL, Storage API, Kong (шлюз), PostgREST.
- **Требования:** +2 ГБ памяти под контейнеры Supabase.
- **Минус:** больше движущихся частей, которые нужно обновлять.

### Вариант Б. MinIO — переписывается один файл

MinIO — объектное хранилище по протоколу S3. Приложение сейчас использует
клиент Supabase, а не S3, поэтому нужен переход на `@aws-sdk/client-s3`
и `@aws-sdk/s3-request-presigner`.

- **Правок в коде:** один файл, восемь функций — `createUploadUrl`,
  `createDownloadUrl`, `deleteObject`, `objectExists`, `objectSize`,
  `ensureBuckets` и два помощника имён. Остальное приложение вызывает
  их через тот же интерфейс и не трогается.
- **Оценка:** один рабочий день с проверкой загрузки и скачивания.
- **Плюс:** одна лёгкая служба вместо стека Supabase; S3 — общий протокол,
  под него встают и другие хранилища.

**Рекомендация.** Вариант Б. Разовая стоимость — один день, дальше служба
проще в сопровождении, а весь стек Supabase на своём сервере избыточен:
из него используется только хранилище (аутентификация в проекте своя,
на Auth.js).

---

## Требования к серверу

| Параметр | Минимум | Рекомендуется |
|---|---|---|
| Ядра | 2 | 4 |
| Память | 4 ГБ | 8 ГБ |
| Диск | 50 ГБ SSD | 100 ГБ SSD |
| ОС | Ubuntu 22.04 LTS | Ubuntu 24.04 LTS |
| Канал | 100 Мбит/с | 1 Гбит/с |

Оценка исходит из 3000 обучающихся и до 300 одновременных сессий. Основной
рост диска даёт хранилище работ: планировать по 2—5 ГБ на программу в год.

**Дополнительно нужно:**

- доменное имя третьего уровня, например `lms.tashenev.edu.kz`,
  с записью A на адрес сервера;
- открытые порты 80 и 443 наружу; порт 5432 наружу **не открывать**;
- почтовый ящик или SMTP-реле для уведомлений (необязательно на старте);
- место под резервные копии вне этого сервера.

## Порядок работ

### День 1. Сервер

```bash
# Обновление и базовые пакеты
sudo apt update && sudo apt upgrade -y
sudo apt install -y curl git ufw fail2ban

# Межсетевой экран: наружу только SSH и HTTPS
sudo ufw allow OpenSSH
sudo ufw allow 80,443/tcp
sudo ufw enable

# Docker
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER
```

Отдельный системный пользователь под приложение, вход по SSH только
по ключу, парольная аутентификация отключена.

### День 2. База данных

```bash
sudo apt install -y postgresql-16 postgresql-contrib
sudo -u postgres psql -c "CREATE USER lms WITH PASSWORD 'СИЛЬНЫЙ_ПАРОЛЬ';"
sudo -u postgres psql -c "CREATE DATABASE tu_courses OWNER lms;"
```

В `postgresql.conf` оставить `listen_addresses = 'localhost'` — база не должна
быть доступна снаружи. Приложение и база на одной машине.

Развёртывание схемы из репозитория:

```bash
git clone https://github.com/kanojjand/TU_Courses.git
cd TU_Courses
npm ci
# DATABASE_URL и DIRECT_URL уже указывают на локальную базу
npx prisma migrate deploy      # схема из файлов миграций
npm run db:rls                 # RLS на всех таблицах
```

> `connection_limit=1` в строке подключения нужен был для транзакционного пула
> Supabase. На своей базе это ограничение снимается: `?connection_limit=10`.
> Страницы, где запросы шли последовательно ради одного соединения, станут
> заметно быстрее — сама правка не требуется, но выигрыш появится.

### День 3. Файловое хранилище

По варианту Б:

```bash
docker run -d --name minio --restart unless-stopped \
  -p 127.0.0.1:9000:9000 -p 127.0.0.1:9001:9001 \
  -v /srv/minio:/data \
  -e MINIO_ROOT_USER=lms \
  -e MINIO_ROOT_PASSWORD=СИЛЬНЫЙ_ПАРОЛЬ \
  quay.io/minio/minio server /data --console-address ":9001"
```

Создать бакеты `materials` и `submissions`, **приватные** — публичный доступ
к ним недопустим по разделу 6.3 ТЗ. Затем правка `src/server/storage.ts`
на S3-клиент (см. развилку выше) и проверка: загрузка задания студентом,
скачивание преподавателем, срок жизни подписанной ссылки.

### День 4. Приложение

`Dockerfile` со сборкой Next.js в режиме `standalone`, `docker compose` с тремя
службами: приложение, MinIO, обратный прокси.

Caddy как прокси — он сам получает и продлевает сертификат Let's Encrypt:

```
lms.tashenev.edu.kz {
    reverse_proxy app:3000
}
```

Переменные окружения переносятся из настроек Vercel в файл `.env` на сервере
(права `600`, владелец — пользователь приложения). Меняются:

| Переменная | Новое значение |
|---|---|
| `DATABASE_URL` | `postgresql://lms:пароль@localhost:5432/tu_courses?connection_limit=10` |
| `DIRECT_URL` | то же самое |
| `AUTH_URL` | `https://lms.tashenev.edu.kz` |
| хранилище | адрес и ключи MinIO |

**Переносятся без изменения:** `AUTH_SECRET`, `IIN_ENCRYPTION_KEY`,
`CRON_SECRET`.

> `IIN_ENCRYPTION_KEY` менять нельзя. Ранее зашифрованные ИИН расшифровываются
> только этим ключом; при замене они станут нечитаемыми безвозвратно.
> Ключ переносится первым и сохраняется в защищённом хранилище университета.

### День 5. Перенос данных

```bash
# Снятие копии с текущей базы (по DIRECT_URL, сессионный режим)
pg_dump "$OLD_DIRECT_URL" --no-owner --no-acl -Fc -f dump.pgc

# Загрузка в новую
pg_restore -d "postgresql://lms:пароль@localhost:5432/tu_courses" \
  --no-owner --no-acl dump.pgc
```

Файлы из Supabase Storage выгружаются в оба бакета MinIO с сохранением путей —
ключи объектов хранятся в таблице `attachments` и должны совпасть.

**Сверка после переноса:**

```sql
SELECT 'users', count(*) FROM users
UNION ALL SELECT 'enrollments', count(*) FROM enrollments
UNION ALL SELECT 'period_grades', count(*) FROM period_grades
UNION ALL SELECT 'attachments', count(*) FROM attachments
UNION ALL SELECT 'audit_log', count(*) FROM audit_log;
```

Числа должны совпасть со старой базой. Отдельно проверить, что каждому
`attachments.storageKey` соответствует объект в хранилище.

### День 6. Резервное копирование

Ежедневная копия базы, еженедельная — хранилища, вывоз копий за пределы
сервера:

```bash
#!/bin/sh
# /usr/local/bin/lms-backup — запуск systemd timer раз в сутки
set -e
STAMP=$(date +%F)
pg_dump "$DATABASE_URL" -Fc -f "/srv/backup/db-$STAMP.pgc"
find /srv/backup -name 'db-*.pgc' -mtime +30 -delete
```

> **Копия без проверенного восстановления копией не считается.** Критерий
> приёмки № 12 требует именно проверки восстановления. Порядок: развернуть
> копию на отдельной базе, запустить приложение против неё, войти под тремя
> ролями, сверить контрольные числа. Оформляется актом.

### Дни 7—8. Приёмка и переключение

1. Прогон всеми ролями на новом адресе по сценариям из `docs/ROLES.md`.
2. Проверка: вход, ИУП, регистрация, посещаемость, оценка, апелляция,
   загрузка и скачивание файла, печать транскрипта, все три языка.
3. Нагрузочная проверка на этой инфраструктуре — критерий приёмки № 14.
4. Переключение записи DNS на новый адрес.
5. Старая площадка держится в режиме чтения ещё две недели, затем данные
   на ней удаляются, а удаление оформляется актом.

## После переноса

| Задача | Периодичность |
|---|---|
| Проверка резервных копий | еженедельно |
| Восстановление из копии на тестовую базу | ежеквартально |
| Обновления безопасности ОС | ежемесячно |
| Продление сертификата | автоматически (Caddy) |
| Просмотр журнала аудита | ежемесячно |
| Обновление версии приложения | по мере выпуска |

Периодические задачи, которые на Vercel выполнял планировщик, переносятся
в `systemd timer`: они дёргают те же адреса `/api/cron/*` с заголовком
`Authorization: Bearer $CRON_SECRET`.

```
# /etc/systemd/system/lms-cron-daily.service
[Service]
Type=oneshot
ExecStart=/usr/bin/curl -fsS -H "Authorization: Bearer СЕКРЕТ" \
  https://lms.tashenev.edu.kz/api/cron/daily
```

## Оценка трудозатрат

| Этап | Дней |
|---|---|
| Сервер, база, хранилище | 3 |
| Правка модуля хранилища (вариант Б) | 1 |
| Приложение, прокси, HTTPS | 1 |
| Перенос данных и сверка | 1 |
| Резервное копирование и проверка восстановления | 1 |
| Приёмка и переключение | 1—2 |
| **Итого** | **8—9 рабочих дней** |

По варианту А (Supabase self-hosted) — на день меньше, но сопровождение
сложнее.

Оценка предполагает готовый сервер с доступом и выделенного системного
администратора вуза. Разработчик участвует на этапах правки хранилища,
переноса данных и приёмки.

---

## Что нужно от университета

1. Виртуальная машина или физический сервер по требованиям выше, доступ по SSH.
2. Доменное имя третьего уровня и право менять записи DNS.
3. Системный администратор — на неделю, в основном на первых трёх днях.
4. Место под резервные копии вне этого сервера.
5. Защищённое хранилище для `IIN_ENCRYPTION_KEY` и `AUTH_SECRET`.
6. Решение, кто выступает оператором персональных данных и подписывает акт
   удаления данных со старой площадки.
