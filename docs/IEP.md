# Модули GRP, ACAD, IEP — группы, календарь, индивидуальный учебный план

Этап 3 раздела 8 ТЗ. Документ фиксирует, где реализовано каждое требование
разделов 4.3–4.5, и какие отклонения от ТЗ приняты.

Загрузка демонстрационных данных этапа:

```bash
npm run db:seed:iep
```

Скрипт заводит учебный год, академические периоды с длительностью по R-10,
открытые окна регистрации, график учебного процесса, группу ТАР-26-1к по
плану 6В01601, трёх обучающихся с эдвайзером и реализации дисциплин первого
семестра. У одной реализации квота на два места — на ней проверяется лист
ожидания.

---

## Сквозной сценарий

Результат этапа 3 по разделу 8 ТЗ — «студент формирует ИУП и регистрируется
на дисциплины». Путь целиком:

1. Студент → `/my/iep`. Обязательные дисциплины подставлены, элективные
   выбирает сам, счётчик кредитов считает на лету. → «Отправить эдвайзеру».
2. Эдвайзер → `/advisor`. Очередь ИУП в верхней карточке. → «Согласовать»
   или «Вернуть» с комментарием.
3. Офис Регистратора → `/admin/ieps`. → «Зафиксировать».
4. Студент → `/my/iep`. Открылась регистрация на реализации дисциплин.

## Разделение ответственности

Текущее значение и история хранятся рядом:

| Текущее значение | История |
|---|---|
| `StudentProfile.groupId` | `GroupMembership` — период членства и основание |
| `StudentProfile.advisorId` | `StaffAssignment(kind: ADVISOR)` — период действия |
| `StudyGroup.curatorId` | `StaffAssignment(kind: CURATOR)` |
| `StudentProfile.status` | `StudentStatusHistory` — приказ, основание, даты |

Так требование «с периодом действия и историей» (F-GRP-02, F-GRP-05)
выполняется, а уже работающие запросы по `groupId` и `advisorId`
не переписываются. Обновляются они всегда вместе, одной транзакцией.

`Course` играет роль `course_offering` эталонной схемы: дисциплина в
конкретном академическом периоде. `Enrollment` — это `registration`:
к нему добавлены `status`, `attemptNo`, `waitlistPos` и ссылка на строку ИУП.

## Правила

| Правило | Где проверяется | Уровень |
|---|---|---|
| R-09 — ориентир годовой нагрузки 60 кредитов | `checkIep` | предупреждение: отклонение допускается с обоснованием |
| R-10 — длительность периода ≥ 15 / 10 / 7 недель | `checkPeriodDuration`, `setPeriodDuration` | блокирующее |
| R-13 — из элективной позиции выбирается ровно `chooseN` | `checkIep`, `submitIep` | блокирующее |
| R-14 — регистрация невозможна без освоенных пререквизитов | `buildIepPlan` (показ причины) и `registerForCourse` (запрет) | блокирующее |
| R-15 — ИУП утверждается до регистрации | `registerForCourse` | блокирующее |
| R-16 — F даёт повторное изучение, FX — только пересдачу | `loadStudentHistory`, `nextAttemptNo` | логика попыток |

Жёсткие лимиты кредитов (`I-MIN-CREDITS`, `I-MAX-CREDITS`) берутся из окна
регистрации вида MAIN и блокируют отправку ИУП.

**Почему R-09 не блокирует.** ТЗ прямо говорит: «нагрузка учебного года —
ориентир 60 кредитов; отклонение по ИУП допускается с обоснованием».
Запрет здесь сделал бы невозможным ИУП студента, догоняющего программу
после академического отпуска.

**Почему освоенная дисциплина недоступна к повторному выбору.** Повторная
сдача ради повышения оценки не допускается (Типовые правила, пп. 45–48).
Исключение — оценка F: она требует повторного изучения, и такая дисциплина
остаётся доступной с пометкой.

## Карта требований

### Раздел 4.3, модуль ACAD

| Требование | Статус | Реализация |
|---|---|---|
| F-ACAD-01 Учебный год → периоды разных видов | 🟡 | `AcademicPeriod` c типами SEMESTER / TRIMESTER / QUARTER / SUMMER. Периоды практик и ИА заводятся событиями графика, а не отдельными периодами |
| F-ACAD-02 График учебного процесса с обозначениями | ✅ | `CalendarEvent`, панель в `/admin/periods` |
| F-ACAD-03 Окна регистрации: основная, add/drop, летний семестр | ✅ | `RegistrationWindow` четырёх видов с лимитами кредитов |
| F-ACAD-04 Валидация длительности периодов (R-10) | ✅ | `checkPeriodDuration`; `setPeriodDuration` отказывает при нарушении |

### Раздел 4.4, модуль IEP

| Требование | Статус | Реализация |
|---|---|---|
| F-IEP-01 Мастер ИУП, обязательные подставляются автоматически | ✅ | `buildIepPlan`, `/my/iep` |
| F-IEP-02 Счётчик кредитов в реальном времени, лимиты вуза | ✅ | Счётчик в `IepWizard` считает на клиенте; лимиты — из окна регистрации |
| F-IEP-03 Проверка пререквизитов, причина недоступности | ✅ | `blockedReason` у каждого варианта |
| F-IEP-04 Маршрут: студент → эдвайзер → офис Регистратора | ✅ | `IepStatus`; `submitIep`, `approveIep`, `rejectIep`, `confirmIep` |
| F-IEP-05 Регистрация с учётом квот, лист ожидания | ✅ | `placeRegistration`, `promoteFromWaitlist` |
| F-IEP-06 Add/drop в установленное окно с историей | ✅ | `dropRegistration`; снятая регистрация сохраняется со статусом DROPPED |
| F-IEP-07 Повторная регистрация при F, номер попытки | ✅ | `nextAttemptNo`; уникальность `[courseId, studentId, attemptNo]` |
| F-IEP-08 Просмотр и печать ИУП | 🟡 | Печать из браузера (даёт и PDF). Отдельного генератора PDF нет |

Язык обучения при регистрации (часть F-IEP-05) не фильтруется: язык
хранится у дисциплины, а не у реализации, и разделение потоков по языку
относится к модели `course_offering`, которая в текущей схеме совмещена
с `Course`. Отмечено как отклонение.

### Раздел 4.5, модуль GRP

| Требование | Статус | Реализация |
|---|---|---|
| F-GRP-01 Карточка группы: шифр, ОП, год набора, курс, язык, форма, куратор, состав | ✅ | `StudyGroup`, `/admin/groups` |
| F-GRP-02 Назначение куратора и эдвайзера с периодом и историей | ✅ | `StaffAssignment`; `saveGroup`, `assignAdvisor` |
| F-GRP-03 Страница группы: состав, GPA, задолженности, дедлайны, чат | 🟡 | Состав, GPA, освоенные кредиты и статус ИУП есть. Задолженности и дедлайны — вместе с этапом 5, чат — этап 6 |
| F-GRP-04 Перевод между группами с историей и переносом регистраций | ✅ | `transferStudent`; регистрации привязаны к студенту и переживают перевод |
| F-GRP-05 Статусы с датами и основанием (приказ) | ✅ | `StudentStatusHistory`; приказ обязателен для отчисления, отпуска, восстановления и перевода |

## Права доступа

| Право | Роли |
|---|---|
| `iep:manage_own` | STUDENT |
| `iep:view_any` | ADVISOR, REGISTRAR, ADMIN |
| `iep:approve` | ADVISOR |
| `iep:confirm` | REGISTRAR |
| `group:manage`, `staff:assign` | REGISTRAR, ADMIN |
| `student:status` | REGISTRAR |

Эдвайзер согласует ИУП только закреплённых за ним обучающихся — проверка
в `requireIepReviewer`, а не только в отборе очереди.

## Что проверено

Юнит-тесты — `tests/iep.test.ts`, 27 тестов на пилотном плане 6В01601:
отбор позиций по учебному году, деление кредитов многосеместровой позиции
между курсами (физкультура: 8 кредитов за 4 семестра → по 4 на год),
полный набор ровно в 60 кредитов на первом и втором курсе, каждое из правил
R-09, R-10, R-13, R-14, R-16 и логика листа ожидания.

Сквозной сценарий пройден на реальной базе: ИУП сформирован (12 дисциплин,
60 кредитов), отправлен, согласован эдвайзером, зафиксирован офисом
Регистратора — все три шага в журнале аудита с разными исполнителями.
Регистрация на реализацию прошла; при исчерпанной квоте студент попал
в лист ожидания на первую позицию; после снятия чужой регистрации офисом
Регистратора место перешло ему автоматически.
